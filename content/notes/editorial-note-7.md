# Editorial note: concluding without overstating

The final movement of the book is stronger than it first appears.

It does not need to claim that Solid is the future of the Web. Its more defensible conclusion is:

> Applications do not have to own the identity, meaning and only useful copy of everything they work with.

The chapters then move through increasing levels of commitment:

1. **The Web as commons**
   Historically, the Web became fertile because public agreements gave outsiders somewhere to connect.

2. **The Web as data**
   Linked data extends the Web’s original trick: documents have addresses, and things and meanings can have addresses too.

3. **The Web as home**
   Solid explores one possible arrangement in which identity, storage and permissions exist independently of applications.

4. **The margin epilogue**
   The book demonstrates that arrangement at the scale of one real component.

This lets the conclusion stay memorable without pretending the experiment has already succeeded.

## Rhetorical stance

Use rhetoric confidently where the book is describing established history or a concrete mechanism.

Use contrast rather than prediction where the book presents a possible future.

The strongest example is:

```text
application -> account -> data
```

versus:

```text
identity -> data -> applications
```

This does not claim that the second arrangement will win. It shows how moving a boundary changes the problem.

The margin component then provides proof at the right scale. It does not prove Solid’s destiny. It proves that another arrangement can be built and used.

## Rhetorical budget

### Chapter 14

One short bridge from the architecture chapter may help:

> Surviving your own mistakes is only part of the problem. The better answer may come from someone else.

Otherwise, the bazaar, streets, standards and castles already carry the argument.

### Chapter 15

One compact clarification may help:

> Portability lets data leave. Interoperability gives it somewhere useful to arrive.

Avoid grand claims about universal meaning. The private-name examples and public identifiers already make the case.

### Chapter 16

Add little or nothing.

Its contrasts already provide the memorable conclusions:

* software moved into the network; the user’s home did not;
* applications can become visitors;
* reusable software can mean replaceable software;
* the Web became an operating system, but the user still needs a home directory.

The chapter already says that Solid may fail. More qualifications would weaken it without making it more honest.

### Epilogue

The epilogue is the strongest evidence in the closing movement.

The reader does not have to accept a prediction. They can inspect a small system built according to the argument.

Give this reveal room:

> If you have connected the margin to your pod, you were not only reading about this architecture.
>
> You were using it.

Do not crowd it with an immediate recap.

## Transition check

* **Chapter 13 → 14:** slightly weak; one short bridge may help.
* **Chapter 14 → 15:** already works.
* **Chapter 15 → 16:** excellent; the question about where data should live is answered by the home-directory chapter.
* **Chapter 16 → epilogue:** excellent; the abstract home directory becomes the reader’s own notes.

## Guiding principle

> **Be confident about the direction, specific about the example, and uncertain about the destination.**

The ending should not say that Solid is inevitable.

It should leave the reader with the sense that applications could be arranged differently, and that this direction is concrete enough to try.
